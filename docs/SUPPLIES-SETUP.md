# 啟用分類庫存、零食手動補貨與新品入庫

網站後台分成「飲料／零食／冰品／泡麵／碳粉」。泡麵與碳粉存放在原試算表的獨立工作表，沿用目前 Google Apps Script 部署網址；原飲料、願望及其紀錄繼續使用。

## 1. 更新原 Apps Script 專案

1. 開啟 [最新版 Code.gs](https://github.com/reytai-hldwn/pantry/blob/main/google-apps-script/Code.gs)，按 **Raw** 開啟純文字，按 `Ctrl+A`、`Ctrl+C` 複製完整內容。
2. 到 [Google Apps Script](https://script.google.com/home)，開啟目前提供網站 `/exec` 網址的原專案。
3. 左側選 **Code.gs**，按 `Ctrl+A` 全選、`Ctrl+V` 貼上，再按 `Ctrl+S` 儲存，等畫面顯示已儲存。
4. 這次不需執行 `setupOnce`。原專案的 Script Properties、原試算表及部署網址會繼續使用。

## 2. 更新目前正在使用的部署

1. 右上角按 **部署 → 管理部署**。
2. 左側選目前網站正在使用的「網頁應用程式」部署。
3. 按右側的 **鉛筆圖示（編輯）**。
4. **版本**選擇 **新版本**，說明可填「批次入庫、口味、人工補貨與首頁摘要」。保留原執行身分與存取設定。
5. 按 **部署**；若 Google 要求授權，使用原帳號完成。
6. 沿用原本的 `/exec` 網址，不必更改 GitHub Variables。

只按儲存不會更新網站呼叫的正式版本，需完成上述「管理部署 → 新版本 → 部署」。

## 3. 回網站確認

1. 開啟 [宏穩茶水間](https://reytai-hldwn.github.io/pantry/)，按 **管理後台 → 倉庫庫存**。
2. 點 **泡麵** 或 **碳粉**。若仍顯示更新提示，按網站右上角 **重新整理**，再確認上一節已更新正確的部署。
3. 下列品項先顯示「待盤點」，沒有預填現有數量：

   | 分類 | 品項 | 單位 |
   | --- | --- | --- |
   | 泡麵 | 來一客海鮮 | 杯 |
   | 泡麵 | 滿漢大餐牛肉麵 | 碗 |
   | 泡麵 | 拉麵道味噌拉麵 | 杯 |
   | 泡麵 | 拉麵道豚骨拉麵 | 杯 |
   | 泡麵 | 奶油白醬辣火雞麵 | 杯 |
   | 泡麵 | 辛拉麵 | 杯 |
   | 碳粉 | 黑色碳粉 | 盒 |
   | 碳粉 | 黃色碳粉 | 盒 |
   | 碳粉 | 紅色碳粉 | 盒 |
   | 碳粉 | 藍色碳粉 | 盒 |

4. 實際清點後，按單一品項的 **盤點**，或上方 **盤點這一類**；填登記人與實際數量。空白保留原紀錄，填 `0` 才代表實際為零。
5. 第一次成功登記時，原試算表會自動新增 `SupplyCatalog`、`SupplyHistory`、`SupplyWarehouse`。前兩張是來源資料，後者是產生的庫存檢視；查閱清單不會建立或改寫紀錄。

## 4. 快速入庫與保存期限

「到貨入庫」分成 **飲料／零食／泡麵／碳粉** 四個子頁，每頁各有入庫表單與最近 72 小時內全部該類入庫紀錄。可從頁面上方切換，或直接開啟 [泡麵到貨入庫](https://reytai-hldwn.github.io/pantry/#restock-noodle)、[碳粉到貨入庫](https://reytai-hldwn.github.io/pantry/#restock-toner)。泡麵與碳粉沿用庫存頁的相同儲存與效期紀錄；未儲存時切換會先提醒。

各類入庫選單依目前紀錄庫存由少到多排列，待盤點的品項排在後方；選單顯示數量，不標記「需要補貨」。飲料、零食與泡麵的「其他／新品」固定在最後。

1. 點品項旁的 **＋ 快速入庫**。
2. 填登記人與本次到貨數量，依該品項的「杯／碗／盒」登記。兩類均不使用整箱換算。
3. **泡麵必填保存期限**，以包裝上的有效日期為準；不能填早於今天的日期。碳粉不需填保存期限。
4. 相同品項若有不同保存期限，分次入庫。每次都會保留自己的批次、原入庫量、日期、登記人及備註，新日期不覆蓋舊批次。
5. 按 **確認入庫**，收到 Google 儲存確認才顯示成功。

總庫存＝最近一次實際盤點＋之後到貨。尚未完成首次盤點時，入庫仍會保存，但總量繼續顯示「待盤點」，不會把未知的原庫存當成零。

## 5. 查看效期提醒

- 泡麵庫存表的 **保存期限／入庫批次** 欄顯示較早的保存期限；展開可查看各批次。
- 預設 **30 天內到期**顯示近效期提示；當日顯示「今天到期」，超過日期顯示「已到期」。判斷以台北日期為準。
- 批次上顯示的是原入庫數量，實際剩餘需現場核對。
- 確認某批已用完或已移除後，按 **此批已用完**、填登記人，再確認，可解除該批提醒。這個標記保留紀錄，總庫存另以實際盤點校正。
- 當實際盤點為 `0` 時，之前各批次的提醒自動結束；原入庫與效期紀錄仍保留。
- 既有庫存沒有保存期限資料時顯示「效期待補」，不推測日期。
- 若盤點既有庫存或上調數量時沒有對應的入庫效期，另顯示效期待核對提示；新入庫的日期不代表舊庫存也已核對。

## 6. 到貨時登記新品

1. 在飲料或泡麵到貨子頁，從品項選單選 **其他／新品**，即可展開品項名稱與單位欄位。碳粉維持固定四色。
2. 填完整品名與口味；飲料選包／瓶／罐，泡麵選杯／碗。新品先按單位填實際到貨量，不做整箱換算；泡麵仍必填保存期限。
3. 填登記人並確認送出。新品與這次到貨使用同一份儲存確認及重試識別碼，重複點擊不會多建品項或多計到貨。
4. 成功後，新品會留在選單及倉庫供後續使用。同名品項需沿用原選項；已停買品項請先核對歷史清單，避免庫存拆成兩份。
5. 首次入庫即建立本次到貨量的紀錄庫存，之後到貨直接累加；已有實際盤點時，以最近盤點加後續到貨為準。舊的已入庫、未盤點商品會由既有紀錄算出數量，不另補盤點或到貨。現場若另有未登記的庫存，請實際盤點校正。
6. 新飲料須選擇飲料分類，單筆與批次入庫都會一併保存；先使用包裝示意圖，包裝暫記「其他」、每箱數量待設定，圖片與營養資訊可之後補齊。後續更新既有品項資料時，沿用它在試算表的 ID，不再重建同名品項。

若已完成上一版泡麵與碳粉更新，這次仍需按第 1、2 節替換最新版 `Code.gs` 並部署新版本，才能使用「其他／新品」。更新前原有入庫繼續使用，新品選項顯示更新提示並暫停選取。

## 7. 補登既有庫存的保存期限

盤點先記下實際數量後，可在 **倉庫庫存 → 泡麵 → 品項旁「補登效期」** 補上現場批次的保存期限，不必再登記一次入庫。

1. 先完成該品項的實際盤點，庫存需大於零。尚未盤點或實際為零的品項不開放補登。
2. 按 **補登效期**，填登記人、每批數量與保存期限。若有不同日期，按 **新增一批** 分開填寫；一次最多 20 批。
3. 各批數量合計必須等於目前庫存。若現場總量不同，先重新盤點；補登不會增減庫存，也不會新增到貨或盤點紀錄。
4. 日期依實物包裝填寫；既有庫存可補登已過期日期，系統會如實顯示到期狀態。
5. 儲存後依本次現場核對結果更新該品項全部效期提醒，過去入庫、盤點及效期紀錄仍保留；批次標示「效期核對」及核對當時數量。之後新到貨繼續保留自己的批次。
6. 若另一裝置在填寫期間更新這個品項，系統會保留輸入並拒絕覆蓋；重新整理並核對現場後再填寫。

此功能需要最新版 Google 部署。先依第 1、2 節更新原專案與原部署；無須執行 `setupOnce`。更新前「補登效期」停用，既有盤點與入庫繼續使用。

## 8. 庫存排序與人工補貨

- 所有分類均可勾選「需要補貨」，不限庫存數量，也允許尚無數量紀錄的商品。已勾選排最前、數字標紅，其他品項按數量由少到多；未知數量放最後。
- 「庫存量少」列飲料 1–10、泡麵 1–3；零食須同時為 1–10 且已勾選需要補貨。飲料、零食與泡麵已確認為0時歸入歷史品項。碳粉的量少範圍維持0。
- 數量少不會自動勾選補貨，也不會因此標紅。入庫、盤點不自動清除人工勾選；取消勾選後恢復一般字色。複製補貨清單只包含當頁已勾選的飲料。
- 舊暫不補貨／準備替換紀錄保存在原稽核表；目前介面以明確的補貨勾選為準，不將舊暫緩設定當作補貨請求。
- Google 部署以 `restockPreferenceEntry.manualAllVersion=1` 啟用全分類人工勾選；舊部署暫停新操作。只需替換完整新版 Code.gs、儲存並更新原部署的新版本，不執行 setupOnce、不換網址。

## 9. 批次多品項入庫

在任一到貨入庫子頁按「批次多品項入庫」，填一次登記人，逐列選分類、搜尋品名或口味、選品項、填入庫數量；可混合四類，最多 30 列。每列以單位數量登記，不做整箱換算。其他／新品可一併填品名、單位；飲料必選飲料分類，零食必選零食分類並可選填口味；碳粉維持四色。泡麵每列必填保存期限，不同期限可分列。

送出前驗證整批資料；某列不正確時不會先寫入其他列，草稿保留。相同商品多列入庫會檢查累計上限。共用一個請求識別碼與儲存回條，連線中斷後沿用原內容重試不重複入庫；每個來源表合併寫入一次，避免逐筆等待多次送出。需 `websiteEntry.batchArrivalVersion=1`。

## 10. 首頁摘要與快速盤點

管理首頁顯示跨品類最近 12 列入庫，以及各類最近一次實際盤點的數字；不同單位分別加總，未盤點的其他商品不推測數量。到貨不冒充盤點。準備補貨、庫存量少清單預設收合，展開後在摘要回應時保持狀態。入口留在功能列。

快速盤點提供飲料／零食／泡麵／碳粉四類；可只填有確認的商品，空白保留、確定用完填 0。首頁只讀一次精簡摘要，不預先載入完整歷史。


## 零食入庫與分類

到貨入庫與倉庫大類依序為「飲料／零食／泡麵／碳粉」。零食分類為：太空包、巧克力、甜/鹹餅乾、健康零食、蛋白質零食、其他鹹食、其他甜食。四款起始商品為多力多滋（超濃起司口味）、多力多滋香菜口味、樂事海苔口味、華元洋芋片（蚵仔煎口味），全部先以太空包、包為單位，數量尚未確認。

零食到貨頁先選分類或輸入品牌、口味、品名，選單即時縮小範圍；這些篩選只使用已讀取資料，不額外呼叫 Google。選不到商品時按「找不到商品？新增零食」，搜尋文字與已選分類會帶入新品欄位，填好單位、數量與登記人後一次儲存，零食免填保存期限。單位支援包、盒、條、個、顆。同名檢查忽略大小寫、全半形及頭尾空白差異，拒絕重複新品時保留輸入。搜尋或切換分類不會默默新增商品，也不會清空已填數量及登記人。

零食每個口味分別保留紀錄數量，按數量由少到多、尚未確認放最後；不以數量自動判斷補貨、不顯示效期提醒。每列均可手動勾選「需要補貨」，不受數量門檻限制；總覽列入全品類共用補貨清單。入庫與更新數量後，勾選會保留到手動取消。泡麵、飲料及碳粉的原有補貨設定與泡麵效期提醒不變。

Google 端透過 `supplyEntry.snackVersion=1` 與 `snackPolicyVersion=2` 啟用免日期零食入庫；手動勾選另需 `restockPreferenceEntry.snackManualVersion=1`。舊部署仍可讀取原品項，尚未更新時新操作會提示更新。只需要把這次完整 `Code.gs` 更新到原部署的新版本，不執行 `setupOnce`、不改網址。前次效能、回購與登記人更正能力都包含在同檔案，之後部署用這份最後版本即可。

`SupplyCatalog` 第六欄 `category` 保存零食分類，第七欄 `flavor` 保存選填口味，其他種類的額外欄位留白。讀取新部署不修改工作表；第一次實際零食／用品寫入才補入必要標題與品項。第六或七欄已有其他用途時拒絕寫入，避免覆蓋。新品與到貨使用相同請求 ID 重試，來源數量、既有批次和其他商品不會被重置。


## 零食紀錄與手動補貨

- 零食數量欄稱為「紀錄數量」，保留最近數量更新與最近入庫日期。這是上次確認加上後續入庫的紀錄值，並非日常取用後的即時餘量。尚未確認過就顯示「尚未確認」，不假設為 0。
- 點「更新數量」可只填一個有確認的品項；空白保留，確認吃完才填 0。它沿用原盤點事件與必填登記人，不會代替其他品項更新。
- 手動勾選「需要補貨」只保存補貨意願與時間，不增減數量；同一個標記跨裝置共用，舊畫面若與新狀態衝突會拒絕覆蓋並提示重讀。總覽的零食手動清單與飲料／泡麵／碳粉的低庫存清單獨立。
- 舊零食日期、效期補登、批次結束事件仍保存在原來源與匯出紀錄，不刪改。新零食入庫可省略日期，網站不顯示零食效期欄位或提醒；泡麵仍要求合法保存期限。
- `RestockPreferences` 的 `consider` 為所有分類的人工補貨請求；零食新標記使用 `normal/consider`，飲料、泡麵與碳粉也支援 `consider` 人工補貨，舊 `hold/replace` 稽核維持可讀。既有零食舊偏好仍可讀取，歷史稽核不重寫。

品名與口味分開填寫；同名不同口味沿用各自 ID。已存在的多力多滋兩款與樂事海苔會按確認的品名／口味讀取，來源歷史保留；其他舊品名不猜測拆分，可由庫存列「編輯品名／口味」補填。編輯不改數量及到貨／盤點事件。口味統計的累計入庫與盤點間估計消耗分開顯示，資料不足不推論受歡迎程度。

## 歷史品項再次入庫

單筆與批次的品名選單也列出歷史品項，放在供應中品項之後並標示「歷史品項」。選取不會改變狀態；送出成功後，沿用原 ID、品名、口味、單位及原紀錄，將本次到貨加進原庫存並恢復供應。若舊帳面數量與現場不同，可再盤點校正，不會自行清零。飲料原圖片與營養資料也繼續沿用。

泡麵重新入庫仍必填保存期限。整批先驗證，錯誤或未送出的列不會先恢復供應；重試沿用原請求，避免重複入庫。舊部署未提供 `websiteEntry.archivedArrivalVersion=1` 時，歷史選項顯示更新提示並停用，原有供應中品項仍可入庫。請使用最新完整 Code.gs 更新原部署，不執行 setupOnce、不換網址。

- 零食倉庫提供搜尋、零食小類與品名兩個下拉篩選；相同品名的各口味一起顯示。切換小類會清除不相容的品名篩選，篩選不讀寫庫存。
- 後台總覽保留收合的「準備補貨」與「庫存量少」區塊，已確認為0的品項統一從歷史品項查看。零食僅列 1–10 且人工勾選的品項；其他庫存範圍不變。
- 零食、泡麵、碳粉的盤點頁與庫存盤點視窗共用含圖示的表格；手機改為直式列，空白不更新、0 表示確認用完。

### 零食品項批次整理

零食的「健康零食」分類取代原「燕麥棒/餅」，舊資料讀取時會自動對應，原庫存與紀錄保留。量販包請在品名註明「（量販包）」，單位為「包」，每個大包算一包；單包棒類用「條」。

`snack-catalog-batch` 僅建立待盤點品項，或核對既有品項後調整品名、口味及分類；不接受庫存或入庫數量，也不新增盤點、入庫紀錄。新品與既有品項以品名及口味核對，原有 ID、單位、啟用狀態及補貨勾選保留。該操作沿用網站請求的收據與重試機制，`supplyEntry.snackCatalogVersion: 1` 表示原 Apps Script 已支援。

### 零食與泡麵零庫存

網站依已登記數量判斷供應狀態：零食與泡麵為0時自動顯示在「歷史品項」，不列入「供應中」；飲料、零食及泡麵的倉庫均不再提供「無庫存」篩選。待盤點不視為0，碳粉維持原規則。來源品項及紀錄保留，有勾選補貨的仍可在準備補貨區查看，總覽不再重複顯示無庫存區塊；重新入庫沿用原ID並恢復供應。手動移入歷史的品項仍須明確選擇重新入庫。這項網站更新相容現有Apps Script，不需重新部署。

### 快速盤點篩選

快速盤點的品項依繁體中文品名筆畫排序，同品名再依口味筆畫排序，英文／數字使用自然順序；可搜尋品名／口味；飲料可依小類篩選，零食可依分類及品項名稱篩選。切換這些篩選只改變顯示的列，保留所有已填數量，送出時一併儲存。狀態列會顯示目前可見品項及已填項數，未填品項保持原紀錄。

## 補貨勾選認證與分類總量

最新版後台的「總量 · 分類查看」以全部品項的最新盤點及後續入庫計算帳面餘量，各單位分開加總。正庫存計入品項數；零庫存不計入項數，待盤點另列。歷史品項若仍有帳面餘量，也會保留在合計並標示為歷史品項。

如需限制「需要補貨」的勾選及取消，先在原 Apps Script 左側 **專案設定（齒輪）→ 指令碼屬性 → 新增指令碼屬性** 新增：

- 屬性：`HOLDWIN_RESTOCK_PIN`
- 值：管理者自訂的 4–12 位數字認證碼（前導零會保留）

儲存屬性，再替換完整新版 Code.gs、儲存，依上方步驟更新原網頁應用程式部署。不用執行任何函式、重建試算表或更換網址。認證碼請只填在私人指令碼屬性，勿寫進公開程式碼、GitHub 檔案或本文件。

首次勾選或取消時會要求認證碼，與該次儲存一併驗證，不另發驗證請求。驗證成功後，同一分頁 30 分鐘內免重填；重新整理或關閉分頁後清除。認證碼不寫入瀏覽器儲存空間、試算表紀錄或查詢網址。每次新勾選仍由資料端檢查；變更私人屬性後，原分頁記住的舊碼會被拒絕並要求重填。

未設定該屬性時保留既有免認證流程；設定了非空但格式錯誤的值時，補貨修改會被拒絕，需由管理者修正。此設定只限制補貨標記，其他既有盤點、入庫與願望操作維持原流程。

## 冰品庫存

更新完整 `Code.gs` 並在原部署選「新版本」即可啟用冰品，不需執行任何函式或 `setupOnce`。專案的補貨認證碼屬性繼續使用。舊部署仍可操作其他分類，冰品顯示更新提示。

冰品與零食平行，在倉庫庫存、到貨入庫、快速盤點和總量摘要各有獨立分類；到貨頁選「其他／新品」填完整品名、單位和數量即可建檔。支援支、杯、盒、包、個、桶，不換算整箱，首次入庫直接建立已知數量；不預建未確認商品或數量。補貨由人工勾選，已勾選且數量 1–10 會出現在庫存量少；0 轉入歷史品項，再次入庫沿用原 ID 與紀錄。冰品這版不要求保存期限、不顯示效期提醒，也不加入飲料冰箱或消耗排行榜。
