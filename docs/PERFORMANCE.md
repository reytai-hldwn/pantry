# 網站載入、送出與飲用人氣

## 載入方式

- 手機沿用原單門插畫的相同 347 × 475 像素區域，抽出為無損 WebP，提早載入；不再為該區域下載完整設計稿。
- Logo 使用正式原檔產生的 160 像素顯示副本，圖示另用 64 像素副本；原檔保留。
- 飲料架與桌機開門內景使用顯示尺寸 WebP，剪影與裁切座標沿用原照片；飲料詳細資訊仍使用原檔。
- 關門不指定飲料照片的 `src`；開門才啟用原生延遲載入。
- `pantry-ui.woff2` 包含目前介面與品項用字，罕用新字依 Unicode 範圍按需下載補充片段，不再下載 5.3 MB 完整字型。
- 已驗證的公開清單最多保留 24 小時，回訪先顯示上次資料並背景重讀 Google。快取綁定部署網址；倉庫數量、盤點紀錄不寫入這份快取。快取過期、格式有誤或瀏覽器不允許儲存時，正常讀取 Google。

顯示素材可用 `node scripts/build-display-assets.mjs` 重建，需要 ImageMagick、fontTools 與 Brotli；產物已提交，正式 CI 不需要這些額外工具。所有原始圖檔仍保留。

## 量測

2026-11-02 本機瀏覽器對照：390 × 844、CPU 4 倍降速、80 ms 網路延遲、750,000 bytes/s 下載、Google 回應模擬為 1.5 秒。每次皆使用空快取，關門後等候 6 秒，再開門等候 4 秒。

| 指標 | 優化前 | 優化後 |
| --- | ---: | ---: |
| 關門階段已完成傳輸 | 3,958,799 bytes | 806,380 bytes |
| 開門階段累計已完成傳輸 | 8,356,633 bytes | 1,141,778 bytes |
| 手機背景單一資源下載時間 | 9,475 ms | 993 ms |

關門傳輸減少約 80%。這些是指定條件下的資源量測，不是每台手機的開站時間保證。首次使用仍須等待 Google 回應；回訪快取的整合測試會刻意扣住 Google 回應，確認清單可先顯示並操作。

## 熱門飲料

冰箱內上方顯示前三名與「平均每週」。計算方式是相鄰兩次盤點間的「前次盤點＋中間入庫－本次盤點」，除以觀察工作日天數後乘以 5，採最近 30 天滾動統計。依容器數排名，單位保留包／瓶／罐；不是本週逐次取用紀錄，也不是銷售額或點閱次數。

至少兩次盤點、連續有效觀察合計滿一個工作日，才顯示估算；未記錄入庫造成的負消耗、異常與停買品項不參加排名。沒有足夠紀錄時顯示「累積盤點中」，有效紀錄為零消耗時不列假排名。

新版統計在第一次開門後獨立讀取 `popularity` 摘要端點；舊部署沿用 `warehouse` 端點，不改變目前頁面、公開清單或管理狀態；只保留計算後的摘要，1 分鐘內重開沿用。盤點、入庫或新增品項成功後使摘要過期。端點網址沿用原部署；完整改善需更新 Code.gs 並發布原部署的新版本。

整合測試 `tests/browser-mobile-performance.mjs` 驗證關門零飲料照片下載、正確扣除入庫、統計等候時可搜尋與切頁、回訪先顯示清單，以及背景回應保留未送出表單。


## 桌機、後台與送出流程（2026-11-02）

- 桌機兩種原尺寸插畫改用品質 90 的 WebP；橫幅由 2,316,448 bytes 降為 234,416 bytes（約少 90%），窄高版由 2,249,839 bytes 降為 210,332 bytes。原始 PNG 保留。桌機首頁預先下載常見橫幅，手機與其他入口不下載桌機插畫。
- 同類資料的重疊讀取共用同一請求；已確認寫入後，較早發出的讀取不能蓋掉新資料。從後台返回前台可立即使用剛驗證的公開欄位，再背景重讀；不把庫存與紀錄保留在公開快取。
- 後台總覽入口立即顯示，低庫存摘要獨立讀取 `admin`。摘要含飲料、泡麵、碳粉的 10 以內品項、暫不補貨狀態與願望待評估數；不開啟 Google Forms、不讀取投票名單、不傳回整份紀錄。不足資料的品項不當作 0。僅記憶體保留 15 秒，庫存寫入後失效。舊部署自動以原倉庫端點相容讀取。
- 許願／贊同不再計算、重畫庫存工作表。伺服器完成持久儲存後，回條帶回該筆願望與票數；網站驗證目標和欄位後直接更新，省下一次完整清單讀取。很大的贊同名單或舊部署沿用完整重讀。
- iframe 回應載入可以提早查詢回條；載入本身不代表成功。回條確認、固定請求 ID、防重複與超時後保留原輸入的規則仍保留。
- 固定表單網址依表單 ID 在 Script Cache 暫存 6 小時；完成回條也可暫存。沒有快取仍以來源資料處理，未完成的回條不快取。庫存、願望與原始紀錄不做伺服器資料快取。原生飲料寫入只在會影響已封存品項的重試中重畫封存工作表。

受控 Chromium 對照（虛構資料，POST 延遲 400 ms、回條 200 ms、公開讀取 1,200 ms）：

| 流程 | 原桌機 | 新桌機 | 原手機 | 新手機 |
| --- | ---: | ---: | ---: | ---: |
| 送出許願至畫面更新 | 3,033 ms | 1,429 ms | 2,913 ms | 998 ms |
| 贊同至畫面更新 | 3,193 ms | 1,262 ms | 2,923 ms | 1,019 ms |
| 後台返回冰箱 | 1,509 ms | 92 ms | 1,402 ms | 70 ms |

同一流程完整資料讀取由 5 次降為 3 次。這是相同模擬條件的流程比較，不包含真實 Apps Script 的啟動時間保證。正式端點唯讀單次基線約為公開 7.85 秒、倉庫 6.22 秒、未完成回條 2.34 秒；因此省去整份重讀有實際價值，Google 本身回應較慢時仍需等候。

`tests/performance.test.mjs` 驗證來源工作量、回條快取提交順序、過時回應保護、統計同算法與獨立摘要；`tests/browser-performance.mjs` 可設 `PANTRY_BASELINE_ROOT` 對照舊版。`tests/browser-admin-archive.mjs` 驗證總覽不等候完整紀錄、10 以內優先、暫停補貨的一般字色，以及歷史品項回購的共用票數。


## 動態標題字型

正式站驗證時發現，許願名稱只要出現精簡檔未收錄的字，就會下載完整 `pantry-hand-complete.woff2`（5,312,160 bytes）。補充字型現改為按 Unicode 範圍載入的片段，每片包含最多 512 個尚未收錄字元；常用固定標題仍只載入約 296 KB 精簡字型，字形與字距不變。完整檔保留作為來源與離線預覽，正式 CSS 不引用。`tests/browser-font-loading.mjs` 會實際新增兩個不同片段的罕用標題字，確認只下載對應片段且沒有完整字型請求。

2026-11-02 桌機與手機瀏覽器實測，兩個不同片段的補充字元共下載 325,580 bytes；完整字型請求為 0，較原先 5,312,160 bytes 約少 94%。共 42 片、每片最大 218,248 bytes；另以來源字型驗證所有 Unicode 覆蓋完整、片段不重複，以及每片探測字元的字距相同。


## 盤點儲存與量販包單位（2026-11-18）

原本盤點收到確認回條後，仍會等待一次完整倉庫讀取才解除儲存狀態。新版飲料、零食／冰品／泡麵／碳粉與咖啡豆盤點，在提交回條附帶有效的 `stocktake.version: 1` 時，先套用資料端已提交的數量、品項狀態與異動，再解除儲存狀態。完整資料改在背景同步；原有輸入保護會保留同步期間新填的盤點內容。

回條須符合原請求代號、操作、品項與數量，通過既有 Google 資料驗證，且不能早於已讀取快照。只套用已確認提交的資料，不在送出時預先改數字。未確認、舊部署、不完整或不吻合的回條仍沿用完整重讀；過大的回條移除局部資料，以免超過試算表單格 40000 字元限制。部分更新不會將整份庫存標為最新，原 30 秒記憶體快取會失效，背景讀取成功後才恢復完整快照。盤點後熱門統計也會失效重算。

資料端的主要減量：

- 既有庫存檢視只更新資料列，保留相同格式與靜態標題；飲料供應品項數改變（例如歸零進歷史）時，仍使用完整重建。原始來源紀錄不清除。
- 用品工作表只有初次建立或補欄位才設定標題格式；日期格式只處理新增紀錄的兩欄，不再重設全部歷史。
- 歷史紀錄先排序與分組一次，再取得各品項餘量，減少逐品項重掃整份歷史。儲存回條共用這次已讀取的庫存與事件，不另讀許願或表單資料。
- 原請求日誌、三次 `flush`、提交後才接受回條、相同請求重試去重、歷史與效期規則皆保留。中斷後重試會回傳當時最新的實際餘量，包含中斷期間其他已完成入庫。

以舊版 `e7f644c` 和本版在相同虛構資料量測（2000 筆用品歷史、既有格式與請求日誌），盤點時試算表讀寫／格式操作次數：飲料 **28 → 12**，用品 **31 → 15**；用品格式設定範圍 **4018 → 16 格**（含固定請求日誌欄位）。這是模擬的呼叫數，不代表正式 Google 服務的實測秒數；冷啟動、鎖等待與網路時間仍會影響實際體感。

重現呼叫量：`PANTRY_BASELINE_CODE=/舊版/Code.gs node tests/bench-stocktake.mjs`。正確性與重試：`node tests/stocktake-speed.test.mjs`。手機／桌機：`node tests/browser-stocktake-speed.mjs`，故意暫停完整倉庫回應，確認儲存已解除等待、已確認數字顯示正確，且繼續輸入不會被背景同步覆寫。

此優化需要將最新完整 `google-apps-script/Code.gs` 貼回原專案、儲存，再在原部署選「新版本」部署，不需重跑 `setupOnce` 或更換 `/exec` 網址。未更新 Google 端時，網站仍採用原本的完整重讀流程。

「鴻津玉米棒」依使用者確認固定使用量販包的 **包**：整個量販包算 1 包，不換算內袋或單條。舊資料讀取會統一為包；下一次正式用品寫入只校正該品項的來源單位欄，保留原 ID、品名、數字、補貨勾選與舊歷史，不套用其他品牌的玉米棒。

## 補貨勾選儲存（2026-11-18）

補貨勾選原本會在驗證、寫入稽核及更新檢視時，重讀同一張 `RestockPreferences` 的標題、完整紀錄和事件 ID。新版只在同一次持有網站鎖的請求內共用已讀資料；寫入前仍核對欄位，若工作表被直接追加資料，會重新讀取再附加，保留新資料。重試會重讀目前狀態，先前已提交的標記不重複新增，也不把較新的取消蓋回去。姓名必填、`expectedMode`、原請求指紋、持久日誌與三次 `flush` 都保留；沒有建立跨請求的補貨資料快取。

同樣 2000 筆虛構補貨紀錄、既有檢視與請求日誌，比對前版 `5d89e05`：飲料、零食、冰品、泡麵及碳粉每次正常勾選的範圍讀取均由 **12 → 7 次**；讀取儲存格由約 **30000 → 14000 格**。寫入仍為 4 次、提交確認仍為 3 次。這是模擬的 `getValues` 呼叫與資料量，並非正式 Google 服務的秒數。

網站仍優先接受提交 iframe 傳回的已提交回條。若補貨的直接訊息與載入提示未送達，備援回條查詢改為約 **1.2 秒**開始，原為 8 秒；查到 pending 仍等待，只有 accepted 才確認成功。其他操作沿用原等待設定，不增加整份庫存讀取。受控桌機／手機測試在約 1.3 秒收到首次備援查詢，並刻意延後提交，確認畫面不會提早顯示取消成功。

重現讀取量：`PANTRY_BASELINE_CODE=/前版/Code.gs node tests/bench-restock.mjs`。回歸測試包含 `tests/admin-speed.test.mjs`、`tests/fast-receipts.test.mjs` 和 `tests/browser-restock-speed.mjs`；全部使用虛構資料，不寫入正式試算表。

網站端發布後即可提早查詢備援回條。Google 端減少讀取需要將最新完整 `google-apps-script/Code.gs` 貼回原專案並儲存，再在「管理部署」選「新版本」部署；沿用原 `/exec` 網址，不重跑 `setupOnce`。Google 冷啟動、鎖等待與網路仍會影響實際儲存時間。
